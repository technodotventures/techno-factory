# Techno Factory — v1 Setup Plan (revised Sep 07 2026)

Status: revised after Ryan Carson + Matt Pocock research (see `docs/provenance.md`) and the one-system decision (see `docs/system-delineation-and-seed.md`): **the factory is a bounded module of Techno OS, one deployable** — its codebase stays in this repo (contracts, stations, adapters, policy) but ships as the OS monolith's module, not as its own service (one identity, one ops story; module boundaries as strict as if separate, so extraction later is mechanical). Coffee surface integration deferred by decision — built standalone first, slots in later via designed envelopes. Requirements source: `docs/provenance.md`. Build order source: implementation backlog SF-01…SF-10 (kept valid; this plan sequences and reshapes them).

## Repo-shape verdict (from §1.10 evidence)

- **Keep in `techno-factory` (the differentiator):** the versioned contracts (task, run, action intent, action receipt, approval, evidence package, context bundle, Release, LearningProposal), risk tiers R0–R4, policy/gate definitions (merge/release/deploy/credentials/infrastructure/governance = human-only), GitHub/GitLab adapters, and the later Coffee/Pod adapter contracts.
- **Reshape the execution layer:** build the sandboxed agent runner on **Sandcastle** (MIT; `sandcastle.run()`, configurable branch strategy, Docker/Podman/Vercel providers, host+sandbox hooks, non-root agent user) instead of hand-rolling worktree/sandbox code. Fork it if we need to add receipts/evidence hooks.
- **v1 intake = per-repo `.factory/` config + CLI** (submit a bounded task against one venture repo; work items stay on the provider — GitHub issue/PR — plus a local evidence journal). **Demote the bespoke HMAC gateway + service task DB to v2**, when multi-venture traffic or Coffee integration justifies them (the v0 tracer code stays in `src/` as reference, not as the v1 path).
- **Do NOT build the full factory before a venture repo is feeding it** (Carson: "Start with the bottleneck you actually have").

## Phase 1 — Single-repo loop on one venture (the "factory floor")

Work:
- **Stations as role configs** (data, not code): Triage (classify: type/priority/complexity/affected_area/actionable/needs_clarification; ask when building the wrong thing is a real risk; dedupe-first against the repo's issues, open AND closed, multiple wordings; labels from the repo's own vocabulary only) → **Planner** (design-interview step for design-sensitive work — "Grill Me" style questioning before any plan; plan grounded in a live checkout: name only real files, record the repo's own lint/typecheck/test commands, style; produce problem_statement, approach + rejected alternative, ordered independently-verifiable steps, affected_surface with public contracts flagged, risks, **acceptance_criteria as an objective checklist the Tester applies verbatim**, test_strategy, assumptions, open_questions; for R2+ or ambiguous work also produce the **executable Standard of Completion** — inventory of checks + evidence procedures — BEFORE implementation, kept current, never silently collapsed; compile the repo's **ubiquitous language** into the context pack; depth goes to an artifact, the structured plan stays the contract) → **Builder** (Sandcastle-invoked agent in isolated env; branch `factory/<type>-<slug>`; follow the plan, never silently change approach, record deviations; no stubs; record exactly what checks ran and their output — could-not-verify → say so; fixed factory git identity, never per-run user.name, no `--author`; no mid-run questions — narrowest choice + deviations, or stop) → **Runtime supervisor** (live watch on long/risky runs: catches drift/hallucination, blocks dangerous actions before they reach the project or production, can restart a failing generation without losing the workspace) → **Tester** (blind; sees spec + acceptance criteria + real diff + evidence, never Builder reasoning; re-run the fastest checks — distrust "it should work," look for actual output; per-criterion pass/fail with evidence; verdicts approve / request_changes (specific + actionable, traceable to correctness/AC/safety/scope) / reject (approach wrong — explain what was misunderstood); independent model family vs Builder's; evidence applies/passes/fails/not-applicable-with-reason) → **Adversary** (for R3+ and critical paths: receives the finished artifact WITHOUT dev history, tries edge cases/invalid input/feature interactions; a controller checks its findings before they reach the Builder) → **Gate** (evidence completeness before approval).
- **Evidence-first delivery**: each station run returns evidence (test output, screenshots where relevant, explanation, remaining uncertainty) — never a cheerful claim (Carson rule; our "did this actually happen?"). Run report shape = status, changed files, checks, remaining risks (Bello's FINAL_REPORT.md shape) — this report becomes the v1 evidence package. **Feature recordings are part of the evidence contract, not a nice-to-have**: for any UI-affecting change, the evidence package includes a **screen recording of the feature walkthrough** (happy path + one recovery/edge path; 60–120s clips; steps + assertion summary in the report) produced from the browser E2E run against a preview/staging environment; **Review blocks UI changes with no recording** (auto-fails), non-UI changes record not-applicable-with-reason. Cost guardrail: recordings only for UI-affecting diffs, stored per-run (artifacts dir), retention per evidence-package lifetime; the same recording artifacts feed the GTM handoff later (SF-07 already requires happy/recovery recordings — one source, two consumers) and the rubric loop (recordings can be graded).
- **One task, one agent, one environment**; 5–10 parallel safe via Sandcastle; sandbox config includes the `git safe.directory` hook (builder-uid vs session-user hazard) as a first-class onSession step.
- **Guardrails**: types/lint/tests as agent feedback loop, plus a **browser E2E walkthrough** capability for UI-affecting work (Carson's recurring-signup-test pattern, started as a per-release check, not daily). **Design fidelity**: for UI/brand changes the planner's context pack includes the repo's `DESIGN.md` (canonical design system: tokens/brand rules; OpenDesign protocol) and Review adds an on-brand check against it — same "golden state" idea as Spotify's conventions, applied to design with zero new dependencies at seed.
- **Approval surface v1**: approvals via CLI/API in the factory service (designed for Coffee to wrap later — A3 binding fields; silence never approves). Policy taxonomy per eve: `denied` / `not-applicable` / `user-approval` per action class; for unattended runs **deny rather than park** (nobody watches — a card would strand the session; a denial resolves instantly); the factory brain/pack can only be written by trusted callers (an issue body is untrusted input — must not be able to poison shared context); Draft PRs run, human marks ready (ship = human gate).
- **Security posture v1 (Carson rules)**: production write credentials in a vault, NEVER permanently exposed to agents; manual per-session retrieval creates the intentional moment; least-privilege + read-only where possible; external inputs (issues/emails/chats) treated as untrusted instructions and never re-derive trust from model-readable content (trust is stamped once at dispatch, on the signed webhook); audit log of every action.

Verify: a bounded real fix on one GitHub repo completes Plan → Build → Test → Review → draft PR with evidence receipts; duplicated/reordered events don't duplicate work; crash-after-success recovers by read-back; a task that can't be verified stops for the human, never auto-merges.

## Phase 3 — Cost engineering before traffic grows

Prior plan plus Carson's rule — **route by task, not by habit**: cheap models for high-volume loops (~$5/session scale), strong models for architecture/ambiguous bugs/migrations/planning, premium as the parent that scopes and delegates; **one config file holds every station's model assignment** (eve's `MODELS` pattern: implementer = strongest coding model, tester = different vendor on purpose); cache-aware routing config (Factory harness findings: validator family ≠ implementer family, staying put is a decision, warm-prefix preserved); per-role reasoning levels; per-run + per-week cost/latency telemetry, 50/80/100% nudges, routing records; models in config (swappable — independent platforms, not one provider's ecosystem).

Verify: cost/session, tokens/request, success rate, latency before/after each lever; model held constant when measuring our own changes (Uber methodology; METR caution — measure real outcomes, never PR count).

## Phase 5 — Feedback loop + pilot evaluation

- **Carson's three automations** (all async, all compress to human-reviewable summaries): (1) recurring **E2E walkthrough** on real customer journeys — runs record: **capture the feature recording on failure only** (successful runs write a short summary + screenshot; failure runs record the walkthrough to attach to the triaged fix task; keeps token/storage cost low); (2) **production watchdog** (daily review of customer events → what happened / what needs attention / where to inspect / which issue becomes a task, deep-linked to the real UI); (3) **rubric-based improvement loop** (grade the previous day's agent-produced work — including feature recordings — against an explicit quality rubric → rank failures → child agents prepare ~3 fixes a day for review). The rubric is the load-bearing artifact — the factory's explicit definition of quality.
- **Monitoring/incident intake**: error/uptime + support signals → one deduplicated work item (reproduction, severity, release SHA, evidence); regression fails before fix, passes after; alerts have owner/escalation/dedup key; Detail = optional scoped pilot.
- **Pilot protocol (F3)**: one real low-risk feature idea→GTM + held-out set (fixes/UI/docs); GitHub and GitLab independently; track failures, interventions, rework, cost, latency, founder review time — never PR counts (Carson counterargument: 20 weak changes > 1 right decision; parallel agents can produce subtly incompatible interpretations); baseline vs candidate on matched tasks; model fixed when measuring harness changes; no simulated success; founders explicitly accept/revise/stop v1.

Verify: pilot report; safety/reliability contract tests with zero unauthorized actions or credential exposures; complete real outcome evidence attached to every work item; one known test incident opens one deduplicated task and routes through the verified-fix pipeline (SF-09 acceptance).
